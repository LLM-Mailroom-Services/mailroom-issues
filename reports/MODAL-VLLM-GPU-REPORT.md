# Modal + vLLM GPU economics — SAND-032

_Qwen3-8B-AWQ on vLLM v0.29.0, Modal L4 GPUs at $0.80/h each · 24 runs, 1,713 documents, 20,406,786 tokens · generated by sandbox `reports/dashboard/export_hub_reports.py` from the cross-checked reports hub (1,376 source-quoted figures, 736 automated cross-checks) · sources: local-mailroom-sandbox @ 8a931d00b068 · eval-environment @ f6bb5107e138 · mailroom-ml @ d3ad22263da0_

This report covers what the self-hosted leg cost and how well it used the GPUs. It answers four questions: what a token costs on a Modal L4, where the GPU money went, how busy the GPUs were, and what adding a second L4 did. Its companions are [COST-COMPARISON-MODAL-VS-API.md](COST-COMPARISON-MODAL-VS-API.md) (cost per document against the hosted API) and [MASTER-REPORT.md](MASTER-REPORT.md).

## Summary

- **Spend.** SAND-032 used $2.80 of its $5.00 cap (fleet-window ledger at close; it stood at $1.21 after stages 1–5). The runs themselves bill at least $2.18: $1.72 while the batch ran and $0.46 of cold boots. The aborted sorter run cost $0.08. The remaining $0.53 (19%) is fleet time outside any run: warm replicas waiting between runs and deploy windows. Only $1.17 (42% of the ledger) paid for GPU slots with a request in flight.
- **Cost per token.** A token costs $0.052 to $0.321 per million on the busy-window basis. At a fixed L4 price the only variable is throughput per L4: $ per 1M tokens = 222.2 ÷ (tok/s per L4). The cheapest run is S6 (LLM sorter, 2×L4 at c32): 98% of its tokens are input, and it ran at 4,237 tok/s per L4. The dearest is S5 (Merger agreements · MAUD prompt, 2×L4 at c32), at 692 tok/s per L4 with long decodes and a long-document tail. Per million *output* tokens the range is $0.82–$4.00.
- **Against the hosted API, per token.** On the same tasks, Modal at 2×L4 c32 is cheaper per token than every hosted model that logged tokens for correspondence and insurance claims, and dearer for corporate records, contracts and merger agreements. Those are busy-window figures. This program's ledger was 1.6× its busy-window GPU $ (boots, idle slots and warm time); at that load Modal is cheaper per token only for correspondence. Hosted Qwen3-8B, the same model family, costs $0.169–$0.306 per 1M tokens.
- **Utilization.** GPU compute (SM) utilization was never sampled. The measured proxy is client-slot occupancy, the share of admitted request slots holding a request. It is 82%–98% on one L4 at c8, 47%–82% across the 2×L4 c32 sweep, and lowest on insurance claims, contracts, merger agreements and merger agreements · MAUD prompt, where one slow document holds the batch open while the other slots drain. Idle slots inside runs cost $0.55 (32% of busy-window GPU $). vLLM recorded no preemptions on any scraped replica, so KV cache was never the constraint.
- **The second L4.** On the same 100 documents, two L4s at c16 finished in 46.1 s against 95.0 s on one L4 at c8 (2.06× faster). Throughput per L4 held (2,579 → 2,654 tok/s), so cost per token moved from $0.0862 to $0.0837 and cost per document stayed flat. p95 latency rose from 11.6 s to 14.4 s. The second L4 pays only if Modal's router spreads the load. With `max_inputs` 64, it sent 97 of 100 requests to one replica: throughput per L4 fell to 820 tok/s and cost per token rose 3.2×. With `max_inputs` 32 at c64 the split was 51 / 49, and throughput per L4 reached 3,141 tok/s (+18% on c16).
- **Boot.** 9 runs started on a cold fleet; each waited 117–219 s for the engine to answer its first request. CUDA-graph capture is most of the difference: deploy → ready went from 123 s at L1 to 216 s at L5. Boots cost $0.46, 21% of the runs' billed GPU $; one cold 2×L4 start at L5 costs $0.096.

## 1. Setup and method

| | |
| --- | --- |
| Model / engine | `Qwen/Qwen3-8B-AWQ` (one bf16 `Qwen/Qwen3-8B` arm), vLLM `v0.29.0`, `max_model_len` 32768, prefix caching on |
| Frozen serving posture (L5) | `awq_marlin`, fp8 KV cache, thinking off, CUDA graphs, `max_num_seqs` 16 (32 on the c64 runs) |
| Fleet | Modal L4 (24 GB), one vLLM replica per container, `min = max` containers pinned for each batch, scaledown 120 s |
| Price | $0.80 per L4-hour (`docs/RUN-COST-DERIVATION.md` in the sandbox) |
| Data | public `Lucius-Morningstar/mailroom-dataset` @ `ed7576b`, seed 42, nested draws (20 ⊂ 50 ⊂ 100) |

**Definitions.**

- **Busy-window GPU $** = wall time of the batch × replicas × $0.80/h. Every $/doc and $/token here uses it, as every SAND-032 run report does.
- **Billed GPU $** = (wall + cold boot) × replicas × $0.80/h. It is a lower bound on what Modal bills for the run: warm time before and after the batch is not in it.
- **$ per 1M tokens** = busy-window GPU $ ÷ (prompt + completion tokens) × 10⁶. Because the GPU bills by time, this equals 222.2 ÷ (tokens per second per L4).
- **Client-slot occupancy** = Σ request latency ÷ (client concurrency × wall). 100% means every admitted slot held a request for the whole batch. The unused share, priced at the busy-window rate, is **idle-slot $**.
- **Effective parallelism** = Σ request latency ÷ wall: how many requests were in flight on average.
- **Per-replica vLLM figures** come from each replica's `/metrics` endpoint. Request counts are deltas over the run; TTFT means and prefix-cache hit rates are cumulative since the replica started.

**Not measured.** No run sampled GPU SM utilization, memory bandwidth or power (no DCGM or `nvidia-smi` sampling), and KV-cache usage was only scraped at idle, where it reads 0%. Occupancy and throughput per L4 are therefore the utilization evidence. See section 6.

**What drives it.**

- **Throughput per L4 is the whole story.** Cost per token is 222.2 ÷ (tok/s per L4), so every lever is a throughput lever. The L0 → L5 ladder raised throughput from 1,261 to 2,238 tok/s on the same 20 documents and cut cost per token 44%.
- **Prompt-heavy work is cheap.** Prefill is fast and prefix caching skips shared system prompts, so tasks dominated by input tokens run at high throughput. The LLM sorter (98% input) reaches 4,237 tok/s per L4.
- **Long documents are expensive.** Contracts and mergers run at 808 and 739 tok/s per L4 at c32. Long decodes are slow, and the last long document holds both GPUs while the other slots have drained (section 4).
- **The bf16 arm costs more for no quality gain.** Unquantised `Qwen/Qwen3-8B` ran at 859 tok/s per L4, 1.8× the cost per token of the L1 AWQ rung on the same documents.

**Findings.**

- **One L4 at c8 stays full.** Occupancy is 82%–98% on the single-L4 runs: eight client slots feed one engine, so a straggler idles one slot in eight rather than most of 32.
- **Wide fleets idle on long tails.** At c32 on two L4s, occupancy drops to 47%–82%. On insurance claims, contracts, merger agreements and merger agreements · MAUD prompt, one slow document is still decoding after the other slots have emptied, so both GPUs bill while mostly idle. Across all runs idle slots cost $0.55, 32% of busy-window GPU $.
- **Doubling admission lowers occupancy.** At c64 (`max_num_seqs` 32) occupancy is 34%–79%: requests queue inside vLLM, latency rises, and wall time falls by less than the extra admission.
- **KV cache was never the limit.** vLLM reported no preemptions on any scraped replica, including the contracts runs at 32 sequences per replica with fp8 KV. Prefix-cache hit rates were 27%–75% per replica.
- **Boot is the other idle.** 9 runs started on a cold fleet and waited 117–219 s for the engine. At L5 the boot was 213 s for an 18 s batch: 92% of that run's billed GPU time.

## 5. Adding the second L4

### 5.1 Same documents, one L4 vs two

- **Near-linear scale-out.** With per-replica admission held at 8, the second L4 cut wall time 2.06× and held throughput per L4, so cost per token and per document stayed flat. The extra GPU buys time, not cost.
- **Tail latency got worse.** p95 rose from 11.6 s to 14.4 s while p50 fell from 6.9 s to 5.7 s. The prefix cache is per replica (70.0% / 50.4% hit rates, against 57.3% on one L4), so shared prompt prefixes are cached once per replica.
- **Routing decides whether the second L4 works.** Modal's `@web_server` router fills a container up to `max_inputs` before using the next. At `max_inputs` 64 and c64, one replica got 97 of 100 requests, its mean TTFT reached 16.2 s, and the batch took 149.4 s. At `max_inputs` 32 the same load split 51 / 49 and took 39.0 s.

### 5.5 What the second L4 costs

- **Per batch, nothing extra while it runs.** Busy-window cost scales with wall × replicas, and wall halves.
- **Boot doubles.** Each cold replica boots separately; at the L5 posture's 216 s, a 2×L4 cold start costs $0.096, half of it for the second L4.
- **Warm idle doubles.** A pinned 2×L4 fleet costs $1.60/h whether or not it has work, which is how $0.534 of this program's ledger was spent outside any run.
- **Verdict.** Add the second L4 when wall time matters and the fleet is fed: client concurrency = replicas × `max_num_seqs`, and `max_inputs` = `max_num_seqs`. For a latency-insensitive batch it gains nothing per token, and it doubles boot and idle exposure.

## 6. Recommendations

1. **Keep the frozen L5 posture and the routing rule.** `max_inputs` = `max_num_seqs` per container, client concurrency = replicas × `max_num_seqs`. This is the largest cost lever measured here.
2. **Match fleet width to document length.** Short documents fill two L4s; long contracts and mergers leave them idle behind one straggler. Split long-document classes into their own batch, or cap their decode budget, before adding replicas.
3. **Stop paying for warm time between runs.** 19% of the ledger bought no run. Queue runs back-to-back against one warm fleet; when the gap to the next run is longer than a cold boot (about 216 s at L5), scaling to zero is cheaper than staying warm.
4. **Cut sorter input, not sorter GPUs.** The LLM sorter is prefill-bound and already the cheapest work per token; head-truncating its input is what moves its cost per document.
5. **Measure real GPU utilization before the next spend.** Sample `nvidia-smi` or DCGM (SM %, memory bandwidth, power) and scrape vLLM KV usage under load. Slot occupancy shows when the fleet is starved; it cannot show how hard a busy GPU is working.
6. **Reconcile the ledger.** Compare $2.80 against the Modal usage page for 27–28 Sep.
