This report covers what the self-hosted leg cost and how well it used the GPUs. It answers five questions: what a token costs on a Modal L4, where the GPU money went, when a warm fleet beats a cold one, how busy the GPUs were, and what adding a second L4 did. Its companions are Cost comparison (cost per document against the hosted API) and Master report.

Summary#

  • Spend. Across every experiment the program has spent $18.93: Modal GPU $14.40 and hosted API $4.53 (cost comparison §5). SAND-032 used $2.80 of its $5.00 cap (fleet-window ledger at close; it stood at $1.21 after stages 1–5). The runs themselves bill at least $2.18: $1.72 while the batch ran and $0.46 of cold boots. The aborted sorter run cost $0.08. The remaining $0.53 (19%) is fleet time outside any run: warm replicas waiting between runs and deploy windows. Only $1.17 (42% of the ledger) paid for GPU slots with a request in flight.
  • Cost per token. A token costs $0.052 to $0.321 per million on the busy-window basis. At a fixed L4 price the only variable is throughput per L4: $ per 1M tokens = 222.2 ÷ (tok/s per L4). The cheapest run is S6 (LLM sorter, 2×L4 at c32): 98% of its tokens are input, and it ran at 4,237 tok/s per L4. The dearest is S5 (Merger agreements · MAUD prompt, 2×L4 at c32), at 692 tok/s per L4 with long decodes and a long-document tail. Per million output tokens the range is $0.82–$4.00.
  • Against the hosted API, per token. On the same tasks, Modal at 2×L4 c32 is cheaper per token than every hosted model that logged tokens for correspondence, and dearer for insurance claims, corporate records, contracts and merger agreements. Those are busy-window figures. This program's ledger was 1.6× its busy-window GPU $ (boots, idle slots and warm time); at that load Modal is not cheaper per token for any task. Hosted Qwen3-8B, the same model that Modal serves as a 4-bit AWQ quantization, costs $0.169–$0.306 per 1M tokens.
  • Cost per token at real utilization. A warm fleet bills by the hour whether or not it has work, so its cost per token is the busy-window figure divided by the share of time the GPUs are busy. Against the cheapest hosted model, a warm L4 fleet stays cheaper only while it is busy more than 69% of the time for correspondence; for insurance claims, corporate records, contracts, merger agreements and sorter the API is cheaper even at 100% busy.
  • Where Modal deployment wins, per document. Run corporate records on self-hosted Qwen3-8B-AWQ (Modal): the measured 1×L4 configuration sand032-s10-corporate75-v2 (v2 prompts) costs $0.00039 per document against Qwen3.7-Flash via the API at $0.00079, 50% less, and scores 0.469 against 0.418. It pays once one warm L4 sustains 1,018 docs/h or a cold batch holds 191 documents. The per-class break-evens are in the cost comparison's §3.
  • Warm vs cold. A cold 2×L4 cycle (the 120 s scale-down tail plus a 216 s L5 boot) costs $0.149, the same as 5.6 minutes of a warm 2×L4 fleet. So stay warm when the next batch starts within 5.6 minutes and scale to zero otherwise. A single cold batch costs 1.1–22.0× its warm cost at the batch sizes measured; the boot stops mattering (under 10% premium) only past 432–10,485 documents per cold 2×L4 batch.
  • Utilization. GPU compute (SM) utilization was never sampled. The measured proxy is client-slot occupancy, the share of admitted request slots holding a request. It is 82%–98% on one L4 at c8, 47%–82% across the 2×L4 c32 sweep, and lowest on insurance claims, contracts and merger agreements, where one slow document holds the batch open while the other slots drain. Idle slots inside runs cost $0.55 (32% of busy-window GPU $). vLLM recorded no preemptions on any scraped replica, so KV cache was never the constraint.
  • The second L4. On the same 100 documents, 2×L4 · c16 finished in 46.1 s against 95.0 s on 1×L4 · c8 (2.06× faster). Throughput per L4 held (2,579 → 2,654 tok/s), so cost per token moved from $0.0862 to $0.0837 and cost per document stayed flat. p95 latency rose from 11.6 s to 14.4 s. The second L4 pays only if Modal's router spreads the load. With max_inputs 64, it sent 97 of 100 requests to one replica: throughput per L4 fell to 820 tok/s and cost per token rose 3.2×. With max_inputs 32 at c64 the split was 51 / 49, and throughput per L4 reached 3,141 tok/s (+18% on c16).
  • Boot. 9 runs started on a cold fleet; each waited 117–219 s for the engine to answer its first request. CUDA-graph capture is most of the difference: deploy → ready went from 123 s at L1 to 216 s at L5. Boots cost $0.46, 21% of the runs' billed GPU $; one cold 2×L4 start at L5 costs $0.096.

Definitions.

  • Busy-window GPU $ = wall time of the batch × replicas × $0.80/h. Every $/doc and $/token here uses it, as every SAND-032 run report does.
  • Billed GPU $ = (wall + cold boot) × replicas × $0.80/h. It is a lower bound on what Modal bills for the run: warm time before and after the batch is not in it.
  • $ per 1M tokens = busy-window GPU $ ÷ (prompt + completion tokens) × 10⁶. Because the GPU bills by time, this equals 222.2 ÷ (tokens per second per L4).
  • Client-slot occupancy = Σ request latency ÷ (client concurrency × wall). 100% means every admitted slot held a request for the whole batch. The unused share, priced at the busy-window rate, is idle-slot $.
  • Effective parallelism = Σ request latency ÷ wall: how many requests were in flight on average.
  • Per-replica vLLM figures come from each replica's /metrics endpoint. Request counts are deltas over the run; TTFT means and prefix-cache hit rates are cumulative since the replica started.

Not measured. No run sampled GPU SM utilization, memory bandwidth or power (no DCGM or nvidia-smi sampling), and KV-cache usage was only scraped at idle, where it reads 0%. Occupancy and throughput per L4 are therefore the utilization evidence. See section 7.

What drives it.

  • Throughput per L4 is the whole story. Cost per token is 222.2 ÷ (tok/s per L4), so every lever is a throughput lever. The L0 → L5 ladder raised throughput from 1,261 to 2,238 tok/s on the same 20 documents and cut cost per token 44%.
  • Prompt-heavy work is cheap. Prefill is fast and prefix caching skips shared system prompts, so tasks dominated by input tokens run at high throughput. The LLM sorter (98% input) reaches 4,237 tok/s per L4.
  • Long documents are expensive. Contracts and mergers run at 808 and 739 tok/s per L4 at c32. Long decodes are slow, and the last long document holds both GPUs while the other slots have drained (section 5).
  • The bf16 arm costs more for no quality gain. Unquantised Qwen/Qwen3-8B ran at 859 tok/s per L4, 1.8× the cost per token of the L1 AWQ rung on the same documents.

4. Warm vs cold GPUs#

4.1 Boot measurements#

  • Deploy → engine ready on the knob ladder: 123 s at L1, 120 s at L2 and 216 s at L5. The L5 changes (fp8 KV, max_num_seqs 16 and CUDA graphs; the program summary attributes the longer boot to graph capture) add about 93 s to the boot and buy the L5 throughput (section 3).
  • Cold starts in the program: 9 runs started on a cold fleet and waited 117–219 s for the engine to answer; the rest ran on a fleet already warm from the previous run (at most 0.5 s to first answer). A run counts as cold when its first answer took at least 60 s (section 8).
  • Scale-down: every fleet kept its containers 120 s after the last request before scaling to zero; that tail is billed.

4.4 Keep warm or scale to zero#

Between two batches with an idle gap G, a pinned warm 2×L4 fleet costs G × $1.60/h. A scale-to-zero fleet pays the gap while the 120 s scale-down tail runs; past that it pays the tail plus the next cold boot (216 s at L5), and the next batch starts that much later.

Idle gap Stay warm (2×L4) Scale to zero (2×L4) Cheaper Added wait
1 min $0.027 $0.027 stay warm none
2 min $0.053 $0.053 stay warm none
5 min $0.133 $0.149 stay warm +216 s cold boot
10 min $0.267 $0.149 scale to zero +216 s cold boot
30 min $0.800 $0.149 scale to zero +216 s cold boot
60 min $1.60 $0.149 scale to zero +216 s cold boot

Rule: stay warm while the next batch starts within 336 s (5.6 min, the scale-down tail plus one L5 boot); beyond that, scale to zero. One cold 2×L4 cycle costs $0.149; a warm 2×L4 hour costs $1.60.

4.5 What SAND-032 paid#

  • Cold boots: $0.46 across 9 cold starts (21% of the runs' billed GPU $).
  • Warm time outside any run: $0.53, the price of about 3.6 cold 2×L4 cycles, or 20 minutes of a warm 2×L4 fleet with no work. The run timestamps needed to split it gap by gap were not exported, so whether each gap should have scaled to zero is not measured here.

Findings.

  • One L4 at c8 stays full. Occupancy is 82%–98% on the single-L4 runs: 8 client slots feed one engine, so a straggler idles one slot in 8 rather than most of 32.
  • Wide fleets idle on long tails. At 2×L4 c32, occupancy drops to 47%–82%. On insurance claims, contracts and merger agreements, one slow document is still decoding after the other slots have emptied, so both GPUs bill while mostly idle. Across all runs idle slots cost $0.55, 32% of busy-window GPU $.
  • Doubling admission lowers occupancy. At c64 (max_num_seqs 32) occupancy is 34%–79%: requests queue inside vLLM, latency rises, and wall time falls by less than the extra admission.
  • KV cache was never the limit. vLLM reported no preemptions on any scraped replica, including the contracts runs at up to 32 sequences per replica (max_num_seqs) with fp8 KV. Prefix-cache hit rates were 27%–75% per replica.
  • Boot is the other idle. 9 runs started on a cold fleet and waited 117–219 s for the engine. At L5 the boot was 213 s for an 18 s batch: 92% of that run's billed GPU time.

6.5 What the second L4 costs#

  • Per batch, nothing extra while it runs. Busy-window cost scales with wall × replicas, and wall halves.
  • Boot doubles. Each cold replica boots separately; at the L5 posture's 216 s, a 2×L4 cold start costs $0.096, half of it for the second L4.
  • Warm idle doubles. A pinned 2×L4 fleet costs $1.60/h whether or not it has work, which is how $0.534 of this program's ledger was spent outside any run.
  • Verdict. Add the second L4 when wall time matters and the fleet is fed: client concurrency = replicas × max_num_seqs, and max_inputs = max_num_seqs. For a latency-insensitive batch it gains nothing per token, and it doubles boot and idle exposure.

7. Recommendations#

  1. Keep the frozen L5 posture and the routing rule. max_inputs = max_num_seqs per container, client concurrency = replicas × max_num_seqs. This is the largest cost lever measured here.
  2. Match fleet width to document length. Short documents fill two L4s; long contracts and mergers leave them idle behind one straggler. Split long-document classes into their own batch, or cap their decode budget, before adding replicas.
  3. Stay warm only across short gaps. 19% of the ledger bought no run. Queue runs back-to-back against one warm fleet; when the next batch starts more than 336 s (5.6 min) later, let the fleet scale to zero (section 4.4).
  4. Size cold batches to their boot. A cold 2×L4 start is worth it only for batches large enough to amortize it: correspondence ≥ 10,485, insurance claims ≥ 3,457, corporate records ≥ 3,798, contracts ≥ 674, merger agreements ≥ 432 and sorter ≥ 858 documents keep the cold premium under 10% (section 4.3). Smaller jobs belong on an already-warm fleet or the hosted API.
  5. Cut sorter input, not sorter GPUs. The LLM sorter is prefill-bound and already the cheapest work per token; head-truncating its input is what moves its cost per document.
  6. Measure real GPU utilization before the next spend. Sample nvidia-smi or DCGM (SM %, memory bandwidth, power) and scrape vLLM KV usage under load. Slot occupancy shows when the fleet is starved; it cannot show how hard a busy GPU is working.
  7. Reconcile the ledger. Compare $2.80 against the Modal usage page for 27–28 Sep (UTC: the vLLM replica start times in the run reports, plus the program summary's stage 6–9 date, 2026-09-28).
